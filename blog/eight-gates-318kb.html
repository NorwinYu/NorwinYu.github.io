BLACK ICE 不是“又一个大模型写的 FPS”。它真正有价值的是：同一套 harness 如何把“能跑”变成“能交付”。

NEON · 无 skill

NEON BREACH 是“能不能写出来”的答案：五波敌人、三阶段 Boss、纯 API 循环，没有 skill，没有产品 gate。它证明模型能生成一个能玩的射击游戏，但它不证明这个游戏能被交付。

BLACK ICE 是同一个问题的后半段。它仍然是一个单文件、零外部素材的浏览器 FPS，但它跑过了一套明确的验收流程：8/8 gates，163 draw calls，127k triangles，12 lights，318 KB。

两个入口

NEON 的入口是“先做出来”。它没有设置页、没有存档、没有触屏适配、没有质量档；它有一个完整的战斗循环，但没有完整的游戏外壳。作为 no-skill control，它非常有用：它告诉你，纯模型循环能到哪一步。

BLACK ICE 的入口是“先定义什么算完成”。它有标题、设置、暂停、失败、结算，有中继站目标、四类敌人、Boss、触屏、音效、性能和移动端检查。它不是把 NEON 加一点 UI，而是在开始写代码之前，先写了拒绝条件。

8/8 是什么

这里的 harness 不是一段更长的 prompt，而是六道核心检查和两项产品检查：

  • Shader：页面没有 shader 编译/链接错误，也没有未捕获的运行时异常。
  • 对象普查：场景里的 mesh、实例和近景道具都有身份，不靠“看不见”蒙混。
  • 碰撞：碰撞和玩家实际使用的移动代码一致，而不是另写一套。
  • 灯光：每盏灯都有实体锚点，不能凭空浮在场景里。
  • 回路：开局、目标、失败、重开能闭环；不是只能截一张图。
  • 观感：在固定机位和固定曝光下检查，而不是靠随机截图碰运气。
  • 产品/移动端：设置、暂停、持久化、触屏、目标链、HUD 和性能预算都要过。

这些检查听起来不体面，甚至有点无聊。但它们正好对应了“demo 看起来完成了”和“游戏真的能玩”之间的差距。

能数的部分

BLACK ICE 的数字很小：318 KB，163 次 draw call，127k 三角形，12 盏灯。这个体量不是靠压缩素材，而是因为它没有素材文件：几何、材质、音效、界面全部由代码生成。小不是目的，小是“内容以函数形式存在”的结果。

但小并不等于简单。它有四个敌人角色、三座中继站、一个 Boss、完整的移动/瞄准/换弹/交互、触屏控制和 6–10 分钟的一局。资源少，循环不少。

Harness 抓到了什么

它抓到的不是“模型不会写代码”，而是那些模型很容易跳过、但玩家一定会撞上的东西：

  • 没有壳：没有设置、暂停、结算和重开，玩家无法真正开始或结束一局。
  • 没有输入闭环：桌面能玩，不代表手机能玩；触屏需要另一套布局和状态。
  • 没有物理契约：视觉上贴地不等于碰撞上贴地；飞机、车辆、玩家都会穿。
  • 没有性能预算：截图能看，帧率不一定能玩；灯光和 draw call 需要上限。
  • 没有可观察性：如果 agent 看不到自己的输出，它只能凭想象验收。
Gate 不是风格 prompt。它是一个可以拒绝你的规则。

这也是为什么 BLACK ICE 的 8/8 值得写：它不是“更漂亮的截图”，而是一组可以被检查、被复现、被拒绝的交付条件。

它没有证明什么

它没有证明 318 KB 就是一个商业 FPS。它是一局 6–10 分钟的单人垂直切片，没有长线成长、叙事密度或网络。它也没有证明 harness 能代替审美：gate 能判断“有没有”，不能判断“好不好”。

它更没有证明“有 skill 一定比没 skill 好”。NEON 仍然是一个完整的 no-skill control；它缺的是产品层，不是模型能力。把两者放在一起，是为了看 harness 到底补上了哪一段，而不是把 NEON 当成失败品。

结论

如果只能从 BLACK ICE 里拿走一件事，我会拿它的验收顺序：先定义完成，再写内容；先让 gate 能说不，再让模型继续生成。318 KB 是一个漂亮的结果，但真正让这个结果成立的，是那 8 道关。
