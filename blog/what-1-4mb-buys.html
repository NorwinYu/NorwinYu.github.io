我把那个独立的 HTML 文件下载下来，拆开看了。第一个意外是，标题里的数字是真的：1,423,668 字节，约 6,195 行，gzip 后约 443KB。第二个意外是，真正有意思的不是 1.4MB，而是零：没有图片文件、没有音频文件、没有 3D 模型文件。

这个游戏叫 Saltline，一个雨夜集装箱码头的第一人称射击 Demo。它经常被描述成“1.4MB 的 3A 大作”。这个说法错得很有信息量：它不是 3A，1.4MB 也不是压缩技术的胜利。它是一个单文件浏览器游戏，内容不是加载进来的，而是运行时用代码生成的。

先拆开这个数字

构成比总数更重要。大约一半是内联进同一个文件的 three.js，另一半是游戏本身：世界构建、材质、shader、玩家与敌人逻辑、关卡数据、UI 和音频合成。

这就是为什么“文件小”这个讨论经常跑偏。传统游戏大，是因为贴图、模型、动画和音频是数据。Saltline 把这些数据换成了过程。代码比它生成的内容小，不是因为它把内容压小了，而是因为它从来没有把内容存下来。

这也不是史无前例。2004 年的 .kkrieger 就用 96KB 装下过一个完整 FPS。真正新的不是“程序化生成”这个想法，而是写生成器的成本：一个模型、一条 prompt、约八小时，以及据创作者说约 550 美元的 API 账单。

零素材，不等于零内容

场景里有集装箱、叉车、防撞墩、灯杆、铁丝网、托盘、木箱、系缆桩、岗亭、楼梯、检修通道和船。它们没有一个是作为 mesh 加载的，而是由一张“套件表”拼出来，尺寸用的是真实米制：

container40:    [12.19, 2.59, 2.44, "paint_blue", "metal"]
container40hc:  [12.19, 2.90, 2.44, "paint_green", "metal"]
jersey_barrier: [3.00, 0.81, 0.60, "concrete", "concrete"]
light_mast:     [0.50, 14.0, 0.50, "steel_galv", "metal"]

场景本质上是一张坐标表，加上一套拼装函数。箱体、圆柱、挤出体、旋转体组合成道具，静态几何合并，重复物体用实例化。所谓“美术”，在这里不是模型文件，而是尺寸、材质键和摆放位置。

表面也一样。没有贴图图集，代码里有约 29 个表面函数：沥青、混凝土、锈、镀锌钢、花纹钢板、瓦楞板、铁丝网、水……再加一张材质预设表，为每种表面补上颜色、粗糙度、金属度、湿润度和宏观色差。启动时把它们算成 height / ORM / albedo，shader 再把 height 转成法线，用三平面投影消除拉伸，叠加水洼、湿润和色差。

内容不是被压缩了，而是从来没有以内容的形式被存下来。

六层生成

1. 几何是套件

36 种道具，真实米制尺寸，用图元拼装、合批、实例化。集装箱不是模型，是尺寸的函数。

2. 表面是函数

噪声、距离场和材质参数生成表面。一张 256×256 的噪声纹理就够，因为细节是算出来的，不是画出来的。三平面投影负责消除接缝。

3. 光照是构图

没有烘焙 lightmap。低角度暖太阳、冷灰雾、天空渐变、PMREM 环境探针、湿地面平面反射，再加一整条后处理：SSAO、体积雾、运动模糊、Karis bloom、自动曝光、ACES、FXAA 和颗粒。

4. 动画是解算

Hound 机器狗不是带骨骼动画文件的角色，而是一棵对象层级加四腿 IK、弹簧阻尼和程序化死亡模拟。动作是参数化系统，不是录制的表演。

5. 音频是合成

雨、风、海、枪声、机械声都由 WebAudio 的 buffer、滤波、waveshaper 和压缩器现场合成，混响的 impulse 也是代码生成。它甚至内置了一个 OfflineAudioContext 自测：离线跑 10 秒脚本场景，检查 peak、RMS、NaN 和削波。

6. 验证是产品的一部分

构建支持固定 seed、截图模式、benchmark、单独运行某个子系统、冻结敌人、指定相机等 URL 参数；把 console 错误收集到 window.__errors；有画质分级，遇到弱 GPU 自动降档。这不是顺手加的。一个没有人类在旁边的 agent，必须能看见自己的输出。

为什么观感更好

我们平时看到的“AI 3D”大多数是场景脚本：一块地、几个盒子、默认材质、一盏平行光、一个随手放的相机。Saltline 是为一个场景写的一套引擎。差距不是某一个 shader，而是一串互相加强的决定。

  • 尺度统一。眼高 1.68m，40 尺集装箱 12.19m，系缆桩 0.7m。人脑判断“真实”靠的是这些小参照物，不是面数。
  • 光线只有一个主意。暖色低太阳对冷灰雾，湿地面反光，强剪影。场景从设计开始就是为了在这种光下被看。
  • 材质有变化。粗糙度、湿度、锈、瓦楞、贴花都在变。单一灰色材质看起来就是塑料。
  • 后处理做了“贵”的那部分。Bloom、曝光、雾、运动模糊和颗粒，把正确的几何变成有空气感的画面。
  • 运动有重量。加速度、coyote time、落地下沉、镜头 bob、ADS 视野、后坐力和震动都参数化了。静帧看不出来，玩几秒就知道了。
  • 细节用来建立尺度。防撞墩、托盘、线缆盘、集装箱编号不是装饰，它们告诉眼睛其他东西有多大。
  • 帧率也是观感。合批、实例化、对象池、半分辨率效果和画质分级，让画面保持响应。

还有一个聪明选择：它避开了程序化最难的主题。没有森林、人脸、布料、毛发或白天。夜景、雨、雾、逆光和湿润的工业表面是宽容的。约束把缺口藏起来，也把对比放大。

为什么旧管线不这么做

程序化内容不新。地形、植被、城市、材质、破坏效果，游戏工业用了几十年。它没有成为默认，不是没人想到，而是不划算。

  • 体积从来不是瓶颈。50GB 蓝光、100GB 下载都很正常。省掉 99% 的体积，不会省掉 99% 的预算；人、迭代和审核才是贵的部分。
  • 玩家记住的是具体性。程序化天然趋向“统计上合理”。英雄资产、角色和关键瞬间仍然要手工做，因为它们需要意图，不是变化。
  • 迭代回路不一样。艺术家习惯直接操作：拖滑块，马上看到。生成器要求把审美翻译成参数，还要先花几个月把工具做出来。
  • 组织风险。外包、认证、法务和单点依赖，都更偏向“很多人能操作的资产管线”。
  • 生成器本身太贵。一个 tech-art 团队可能要花几个月。只有当写生成器变得足够便宜，经济账才会翻过来。

所以真正的变化不是“AI 会写代码”，而是写“造内容的机器”的成本塌了。当生成器比资产便宜，管线就会反过来。

可以借鉴什么

对我自己的实验来说，有用的经验比“做一个 3D 引擎”小得多，也实际得多。

  1. 写生成器，不写内容。任何会重复三次以上的东西，都应该变成参数化系统：道具、HUD、关卡块、材质变体、动画层。
  2. 把验证放进产物里。固定 seed、截图模式、benchmark、错误收集和自测，比另一个 prompt 技巧更有价值。看不见输出的 agent 没法迭代。
  3. 先定光，再建模。一个太阳角度、一个色温、一种天气。构图比细节便宜，但对“看起来贵不贵”的影响更大。
  4. 用米制，用人的相机。眼高、视野、门高、物体尺寸都应该无聊地真实。玩具尺度是最常见的破绽。
  5. 做一条后处理基线。ACES、bloom、暗角、颗粒，四项就能拉开一档。
  6. 用混合管线。重复元素和背景程序化，英雄资产手工或 Blender 辅助。“全程序化”是有效的研究约束，不是所有产品都该采用的策略。
我会保留的一条

一个 build 在能被检查之前，不算结果。Saltline 里最重要的代码也许不是 bloom，而是截图开关、固定 seed 和自测。

它没有证明什么

它没有证明 1.4MB 就是 3A。Saltline 是一段很短的任务：一张地图、少量敌人、简单 AI，没有叙事密度、长线成长，也没有主机认证。550 美元是 API 账单，不含人的审美、筛选和验收。

它也没有证明“全程序化”是正确策略。这个场景成立，是因为它被收得很窄：一个地点、一个时段、一种天气、一个强调色。换成阳光下的森林、角色和布料，同样的方法会暴露所有弱点。

“什么都不下载”也有一个小星号：页面仍然引用了 Google Fonts。严格说，游戏素材是自包含的，但页面在运行时不是完全零请求。

它真正证明的更有意思：模型可以写出一套连贯的内容生成器——几何套件、表面函数、光照、动画解算、音频和测试——再用这套生成器产出一个可玩的东西。资产不再是一个文件，而是一个函数。
