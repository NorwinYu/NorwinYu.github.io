更大的画布。

机场大亨的第一版，是在一个“什么都对”的假设里开始的：既然 three.js 能做出可玩的 3D demo，那把同样的任务交给 Godot，应该只是换一个更大的画布。更多几何、更好的光照、真正的引擎，结果应该更接近成品。

实际发生的是三次返工。第一次，飞机降落时穿进地面；第二次，机场没有滑行道、没有廊桥、没有像样的候机楼；第三次，我要求它“成为一个成品”。每一次都不是模型不会写代码，而是引擎把“看起来完成了”和“真的完成了”分开了。

从浏览器到引擎

浏览器里的反馈回路很短：保存、刷新、截图、看控制台。DOM 和 canvas 都是可检查的，错误通常有一条清楚的栈。Godot 不是这样。它有自己的场景树、资源导入、节点生命周期和导出流程。你要先确认引擎能不能启动，再确认场景有没有加载，再确认相机、光照和碰撞有没有生效，最后才轮到“好不好看”。

这不是缺点，是引擎的代价。它给你真正的 3D 工具，也把反馈拆成了更多层。agent 需要学会的不再是“写一段能跑的 JavaScript”，而是“启动一个项目、读懂它的日志、截一张能判断的图、再改下一个东西”。

这次实验里，最有效的工具不是某个 prompt，而是把 Godot 当成一个可观察的外部程序：用命令行启动，用固定相机截图，用日志确认场景状态。没有这层观察，模型只能凭想象写引擎代码。

第一版像玩具

第一版有飞机、跑道、航站楼，也有起降和收入。它“能玩”，但看起来像把几个盒子放在草地上。原因不是材质不够，而是尺度、层级和机场的基本构件都不对。

一架飞机停在航站楼旁边，如果廊桥没有接上，眼睛立刻知道这是假的。跑道旁边如果没有滑行道，飞机就会像直升机一样原地起飞。候机楼如果只是一排玻璃盒子，没有车道、入口、登机口和塔台的关系，它就不是机场，只是一个有飞机的场景。

这些不是“再生成一点美术”能补的。它们需要一个机场的套件：跑道、滑行道、停机位、廊桥、航站楼、塔台、机库、油库，以及它们之间的空间关系。没有这套关系，模型越努力加细节，画面越像一堆正确的零件。

飞机穿模不是渲染问题

飞机降落时穿进地面，看起来像一个渲染 bug。它其实是状态问题：起落架高度、飞机原点到地面的偏移、跑道的高度、降落动画的最后一帧，只要有一个没对齐，飞机就会陷进去。

这类错误在浏览器里也常见，但 Godot 让它更明显，因为场景有真实的节点层级和碰撞体。你不能只看截图说“差不多”，必须把飞机放到地面上，确认轮子和跑道的接触点。视觉上的“贴地”是一个几何契约，不是一个材质参数。

修完穿模之后，第二层问题才出现：飞机停稳了，但没有廊桥接上；有了廊桥，但没有滑行道把它连到跑道；有了滑行道，候机楼的比例又不对。每修一个“看起来不对”，都会暴露下一层“结构不对”。

机场不是一栋楼

真正的机场是一个流程系统：飞机从跑道脱离，滑行到停机位，廊桥对接，旅客上下，加油、配餐、检修，再推出、滑行、起飞。每一个环节都需要空间和状态。只做一栋候机楼，得到的是一张明信片；做出流程，才得到经营游戏。

于是第二版开始补的不是贴图，而是结构：滑行道、登机口、廊桥、停机位、塔台和机库。飞机不再只是在地面上移动的模型，而是有航班、有排班、有上下客、有维护状态的经营对象。到这一步，游戏才第一次有“机场”的样子。

成品层

“能起降、能赚钱”仍然不是成品。成品需要主菜单、暂停、设置、存档、胜利和破产结算；需要飞机买卖、租赁、转卖、维修和状况衰减；需要航线、票价、需求和八类随机事件。玩家要知道自己为什么赚钱，也要知道自己为什么失败。

这些系统不是“内容”，它们是产品的骨架。没有它们，模拟再真实，玩家也只会在里面逛五分钟。反过来，即使画面朴素，只要循环完整、反馈清楚，玩家会愿意再开一局。

这次返工里，最明显的分界线不是“加了更多模型”，而是“开始有完整的游戏流程”。主菜单、经营、暂停、结算、自动存档，这些看起来不酷的东西，才是从 demo 到产品的分界。

分发也是设计

Godot 给了桌面构建，也拿走了浏览器的一个优势：打开就能玩。机场大亨目前是 macOS / Windows / Linux 工程，没有 Web export。对一个想让人“点开就试”的 demo 来说，这是真实的损失。

这不是说应该回到浏览器。引擎带来的场景能力、光照和工具链是真实的。但它意味着分发要提前设计：是做一个可下载的桌面 demo，还是做一个网页切片，还是录一段两分钟的实际运行？三者服务的目的不同，不能等到最后才决定。

项目最终把工程、截图和说明放进了公开仓库，而不是假装它有一个网页版。这个选择很朴素：有什么就展示什么，不把“未导出的 Web 版”写成“即将上线”。

我学到什么

  • 引擎不是更大的画布，是更长的反馈链。 先建观察工具，再让 agent 写内容。
  • 视觉错误经常是几何契约。 穿模、贴地、廊桥对接，都是坐标和状态问题，不是材质问题。
  • 场景的“像”来自关系，不来自零件。 跑道、滑行道、停机位、航站楼的关系错了，再多模型也不像机场。
  • 产品层要单独预算。 菜单、存档、结算、事件和失败反馈，不能被“再优化一点画面”吃掉。
  • 分发是设计约束。 桌面、网页、视频 demo 是三种产品，不能混着承诺。

如果要再做一次，我会先定三件事：机场的尺度表、一个可检查的固定相机、以及一张“产品层清单”。先让飞机正确地停在地面上，再让它好看；先让一局游戏能结束，再让它变大。
