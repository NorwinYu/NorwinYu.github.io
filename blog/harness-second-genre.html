系统Harness类型迁移

同一个 harness，
换一个类型。

如果 harness 只在 FPS 里有效，它就不是 harness，是一次性 checklist。城市卡丁车是第二次测试。

真正要验证的不是“skill 有没有用”，而是“换一个类型，它还剩下多少”。

NEON BREACH 和 BLACK ICE 证明了 harness 能改变一个 3D 枪战。但这可能只是“射击游戏刚好适合这套检查”。真正的测试是换一个类型：落日环线 和 SUNSET DISTRICT。

四个构建

  • NEON BREACH：无 skill，纯 API，五波 + 三阶段 Boss。
  • BLACK ICE：走 harness，8/8 gates，318 KB，163 draw calls。
  • 落日环线：无 skill，3 圈、860 米、6 台卡丁车。
  • SUNSET DISTRICT：走同一个 skill/harness，4 圈、5 个对手、636 draw calls、539,883 三角形、4 盏灯。

它们不是受控的模型 benchmark：场景、预算和设计目标都不同。它们是一组“换类型后，harness 还能不能工作”的证据。

哪些能复用

能直接搬过去的部分，恰好是那些“和游戏类型无关”的检查：

  • Shader / 页面错误：任何 WebGL 游戏都要先能编译、能启动。
  • 对象普查：赛车和枪战都需要知道场景里有什么、有没有身份、有没有漏掉近景道具。
  • 灯光锚点：每盏灯要有实体来源，不能为了截图凭空加光。
  • 产品壳：标题、设置、暂停、结算、持久化、移动端；这些和类型无关。
  • 移动端：390×844 没有溢出、触控可用；FPS 和赛车都需要。
  • 性能预算：draw call、三角形、灯光数；不同游戏有不同上限，但“要有上限”是通用的。

哪些必须重写

换类型后，最先失效的是碰撞和“回路”的定义。

枪战的 collide gate 假设可步行的矩形空间、货箱坐标和射线遮挡；赛车的世界是一条连续的赛道走廊，有 204 个护栏碰撞体，玩家必须在弯道里被推回赛道，而不是被允许走进建筑。原来的 collision contract 不能直接套用，必须重新表达成“护栏推回 / 墙体夹紧 / 赛道包含 / 进度检查”。

回路也不一样：FPS 的目标是“清完这一波 / 打掉 Boss”；赛车是“四圈内保持前三 / 计时结束 / 车体报废”。产品 gate 仍然存在，但成功条件和失败条件要重写。

输入同样如此。FPS 的鼠标瞄准加 WASD 不能直接迁移到赛车；赛车需要油门、刹车、转向、漂移蓄能、氮气，移动端还需要左右转向区。gate 能检查“触控存在”，但不能替你设计一套好开的触控。

数字

BLACK ICE 的验收是 8/8，318 KB，163 draw calls，127k 三角形，12 盏灯。SUNSET DISTRICT 的验收是 31/31 试玩检查，636 draw calls，539,883 三角形，4 盏灯，390×844 移动端通过。

这些数字不能横向比较“谁更好”。它们说明的是：同一个 harness 能在两个类型里给出可检查的交付条件，但预算和失败模式完全不同。

它没有证明什么

它没有证明 harness 可以原样复制到任何类型。相反，它证明了迁移是有成本的：碰撞契约、成功条件、输入和性能预算都要重写。能复用的是“检查的意识”和“产品层的清单”，不是每一行 gate 代码。

它也没有证明“有 skill 一定更好”。落日环线和 NEON 都是完整的 no-skill 构建；它们缺的是产品层和验收，而不是“不会写”。

结论

如果只看一个类型，harness 很容易被误认为“FPS 专用技巧”。第二个类型暴露了它真正的结构：通用的产品/性能/观察检查可以复用，世界契约必须重写。

这就是为什么我把城市卡丁车放进同一组对比：不是为了多一个 demo，而是为了看这套方法在换类型后还剩下什么。
